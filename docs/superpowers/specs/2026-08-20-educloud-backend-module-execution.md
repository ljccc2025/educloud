# EduCloud 后端模块执行顺序与准备门禁

> 日期：2026-08-20
>
> 状态：执行契约
>
> 范围：后端准备阶段、M01～M13 的交付顺序与每个模块的固定质量门禁

## 1. 目的与覆盖关系

本规格锁定 EduCloud 后端从准备阶段到生产就绪的执行边界、模块顺序和质量门禁。后端按下列顺序逐模块交付，完成一个模块并获得用户确认后，才进入下一个模块。

旧路线图 Task 1 中“批量创建全部空应用”的做法由本规格覆盖，不再作为执行路径。领域边界、安全、数据、API、事件及前后端联调契约仍以 2026-08-18 文档集为准；本规格不重写或替代这些契约。

## 2. 锁定执行顺序

执行顺序如下，任一模块未通过固定门禁时不得跳过或并行推进后续模块：

| 顺序 | 阶段或模块 | 本阶段交付边界 |
|---|---|---|
| 0 | 准备阶段 | 隔离 worktree、父 POM、Rocky 前置检查、共享依赖 Compose |
| M01 | `educloud-common` | 逐模块开发所需的最小公共工程能力 |
| M02 | `educloud-gateway` | 仅完成安全入口基线 |
| M03 | `educloud-user` | 真实认证、会话与授权基础；完成后与 Gateway 再次联调真实登录 |
| M04 | `educloud-file` | 文件生命周期及受控业务绑定 |
| M05 | `educloud-course` | 课程权威数据、维护与学习关系 |
| M06 | `educloud-content` | 按“章节课件、学习进度、作业、考试、社区”顺序交付 |
| M07 | `educloud-order` | 订单及其状态机 |
| M08 | `educloud-payment` | 支付编排、回调和补偿边界 |
| M09 | `educloud-notification` | 可验证的通知领域能力 |
| M10 | `educloud-live` | 直播控制面、聊天和回放元数据 |
| M11 | `educloud-search` | 搜索索引与查询能力 |
| M12 | `educloud-analytics` | 分析聚合视图与指标能力 |
| M13 | `educloud-recommendation` | 可解释规则推荐 |
| 生产就绪 | 生产就绪阶段 | 可观测性、完整 Compose、Kubernetes/Helm、安全、性能、恢复 |

### 2.1 准备阶段边界

准备阶段只建立后续模块共同依赖的工程与运行验证基础：

- 隔离：在专用 worktree 和独立分支中工作，保护主检出中与本阶段无关的变更。
- 父 POM：建立聚合、依赖管理、插件与统一测试入口所需的最小 Maven 父工程。
- Rocky 前置检查：确认 Rocky 环境、容器运行条件、端口与后续验证工具链的前置条件，并记录不能满足的条件。
- 共享依赖 Compose：仅提供 MySQL、Redis、RabbitMQ、Nacos、MinIO、Elasticsearch 等共享依赖的可启动本地编排；不将其表述为完整生产部署。

准备阶段**不提前创建** M01～M13 的服务启动类、Controller、Entity、Mapper、占位接口或业务代码。模块代码只能在其对应的 M 阶段、且在通过失败测试门禁后创建。

### 2.2 模块间联调边界

- Gateway 在 M02 只完成安全入口基线，不以静态登录响应、前端状态或 Mock Token 宣称真实认证已经存在。
- M03 完成后，必须以 User 服务的真实登录、刷新、注销和授权契约与 Gateway 再次联调；M02 的基线不替代这次联调。
- M06 必须严格按章节课件、学习进度、作业、考试、社区的顺序交付；不得为了社区、作业或考试提前建立后续子域的空壳。

## 3. 每个模块的固定门禁

M01～M13 均执行以下固定顺序。所有门禁均须留下可复核证据；失败时先修复当前模块，不将问题转移到后续模块。

1. 阅读对应的 2026-08-18 领域、安全、数据、API、事件、测试和部署文档，并审阅当前 diff。
2. 先写失败测试。
3. 运行测试并确认其因目标行为尚未实现而正确失败。
4. 编写或更新数据库迁移。
5. 实现满足测试的最小后端能力。
6. 运行模块测试。
7. 运行集成测试。
8. 运行全量 Maven 验证。
9. 在 Rocky/Docker 环境验证模块及其依赖。
10. 进行规格审查。
11. 进行质量审查。
12. 向用户汇报结果并等待确认。

“向用户汇报并等待确认”是每个模块完成的必要门禁；未经确认，不开始下一个 M 模块。若外部系统、凭据、容量目标或环境不可用，必须如实报告未验证部分，不能将未验证项标记为通过。

## 4. 能力表述的诚实边界

以下内容只能按其实际实现和验证状态表述，不得用外观、占位实现或演示数据包装为真实后端或 AI 能力：

- 前端 Mock 仍是前端模拟，不是已接入的后端能力。
- 本地通知演示不等于真实通知投递、送达或回执能力。
- 支付沙箱及模拟渠道不等于真实支付渠道接入或资金结算能力。
- 媒体控制面、聊天和回放元数据不等于已具备真实媒体推流、转码或分发能力。
- M13 的规则推荐不等于模型推荐或真实 AI 能力；AI 模型、知识来源、成本和数据权限未经单独决策与实现，不得宣称已集成。

## 5. 生产就绪阶段

生产就绪在 M13 获得确认后单独推进，覆盖可观测性、完整 Compose、Kubernetes/Helm、安全、性能和恢复。该阶段须以已确认的容量、可用性目标、RTO/RPO、密钥管理与恢复演练证据为准；没有这些输入或验证，不编造生产可用性、性能或恢复承诺。

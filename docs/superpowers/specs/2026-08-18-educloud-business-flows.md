# EduCloud 核心业务流程与状态机

> 状态：`【目标设计】`
>
> 原则：状态迁移由服务端命令驱动，客户端不能直接指定任意目标状态。

## 1. 通用状态规则

- 每次状态迁移验证当前状态、操作者权限、资源归属、业务时间和资源版本。
- 迁移成功记录操作者、来源状态、目标状态、原因、时间和追踪 ID。
- 重复命令返回第一次的稳定结果或明确冲突，不重复产生副作用。
- 订单、支付、提交、交卷、审核、发布等关键动作需要幂等键或业务唯一约束。
- 浏览器时间、金额、用户 ID、教师 ID、评分上限和进度百分比都不是可信来源。

## 2. 用户与会话

### 2.1 账号状态

```text
ACTIVE ──失败次数达到阈值──> LOCKED
ACTIVE ──管理员禁用────────> DISABLED
LOCKED ──锁定到期/管理员───> ACTIVE
DISABLED ──管理员恢复──────> ACTIVE
```

规则：

- `LOCKED` 阻止新登录；到期后按配置自动允许重新验证。
- `DISABLED` 阻止登录和刷新，并撤销活跃会话。
- 改密、权限敏感变更和检测到 Refresh Token 重用时撤销相关会话。
- 登录失败不向客户端区分账号不存在和密码错误。

### 2.2 登录流程

1. Gateway 执行 IP/账号限流并生成请求追踪。
2. User 校验账号状态和密码哈希。
3. 创建 Refresh 会话并写登录审计。
4. 返回 Access Token，Refresh Token 写 HttpOnly Cookie。
5. 前端读取 `/me` 初始化当前用户和权限。

任何一步失败都不能产生半有效会话。

Refresh Token 轮换采用会话族：Access Token 的 `sid` 等于 `family_id`。刷新时锁定父 Token 行，原子标记已轮换并插入子 Token；并发宽限窗口外重用已消费 Token 会撤销整个会话族。注销、禁用和改密同样撤销 `sid`，Gateway 立即拒绝族内尚未过期的 Access Token。

## 3. 课程生命周期和审核

### 3.1 状态

```text
DRAFT(vN) → PENDING_REVIEW(vN) → PUBLISHED(vN)
                    │                  │
                    └→ REJECTED(vN)    ├→ OFFLINE → PUBLISHED
                           │ clone     └→ ARCHIVED
                           └→ DRAFT(vN+1)
```

课程根记录持有 `published_version_id` 和 `draft_version_id`。公开 API 始终读取发布版本；教师可以在已发布课程旁维护独立草稿。版本状态与课程生命周期分别保存，API 可向前端映射为单一展示状态。

### 3.2 提交审核

前置条件：

- 操作者是课程负责人或共同授课教师。
- 标题、分类、封面、简介、价格和必要课程内容满足发布校验。
- 当前课程不是审核中或已归档。

处理：

1. Content 审批发布修订时以 `CourseContent` 聚合发布 `ContentRevisionPublished`；Course 消费完整聚合事件流，在本库维护内容就绪投影。首次发布时投影缺失、不就绪或存在版本缺口均失败关闭；后续仅改课程元数据时可复用当前可见内容。
2. 固化课程待审核快照和递增版本号。
3. 将 `course_version` 改为 `PENDING_REVIEW` 并禁止原地编辑。
4. 写审计和 Outbox 事件。
5. Notification 根据事件通知审核人员。

课程进入 `PENDING_REVIEW` 后锁定整个版本；教师若撤回或审核被拒，需要复制出更高版本草稿并使旧审核请求失效。公开课程接口只返回 `published_version_id`，不返回待审草稿。

### 3.3 审批

- 审核人员具备 `course:audit`，且不是提交人。
- 首次发布审批再次锁定并读取本库 Content 就绪投影；投影不就绪或有版本缺口时不切换发布版本，不在审批请求链同步回调 Content。
- 通过后在一个本地事务中把新版本设为 `PUBLISHED`、旧发布版本设为 `SUPERSEDED`，原子切换 `published_version_id` 并发布 `CoursePublished`。
- 驳回时原因必填，原版本固定为 `REJECTED`；教师显式复制为更高版本 `DRAFT` 后才能继续编辑，不能把被审核版本原地改回草稿。
- 已发布课程的标题、价格、封面、核心目录等关键变更需要重新审核。
- 下架不删除课程和历史选课；只有 `OFFLINE` 且当前发布版本、内容就绪投影仍有效时可以重新上架，并写审计/事件。
- 归档只允许草稿/驳回/已下架课程；审核中先撤回、已发布先下架。`ARCHIVED` 为终态，不允许重新销售。

## 4. 课程内容与文件

课程目录使用独立 `content_revision`：公开学习读取 `published_revision_id`，教师编辑 `draft_revision_id`。提交审核后修订及其章节、课件不可变；驳回或撤回后必须复制为更高修订草稿，不能原地改回 `DRAFT`。通过审核时原子切换发布修订，学习中的旧地址按兼容策略保留，不能因教师编辑草稿影响当前学生。

### 4.1 文件上传

```text
创建上传会话 → MinIO 上传 → 服务端确认 → AVAILABLE
                                      │
                                      ├─ 绑定课程/课件/头像
                                      └─ 到期未绑定 → 清理
```

- 上传完成前不能把文件作为业务资源使用。
- 领域服务只接收 `fileId`；File 验证文件状态和访问权。
- 删除业务对象时解除绑定；仍被其他对象引用的文件不能物理删除。

### 4.2 章节和课件

- 教师只能维护所属课程。
- 章节排序在课程内唯一，重排操作在一个本地事务中完成。
- 删除已有学习进度或作业引用的课件时默认改为不可见，不直接删除历史。
- 付费课件的访问地址只向有效选课用户和课程教师签发。

## 5. 购物车、订单和支付

### 5.1 订单状态

```text
PENDING_PAYMENT ──支付成功──> PAID ──退款申请──> REFUNDING
                                          ├─部分成功──> PARTIALLY_REFUNDED ──再次退款──> REFUNDING
                                          └─全部成功──> REFUNDED
       │
       ├─ 用户取消 ──> CANCELLED
       └─ 支付超时 ──> CLOSED
```

### 5.2 支付状态

```text
支付聚合：CREATED → PROCESSING → SUCCESS → REFUNDING → REFUNDED / PARTIAL_REFUNDED
支付尝试：CREATED → ACTIVE → SUCCESS / FAILED / EXPIRED / CANCELLED
异常成功：ACTIVE/EXPIRED/CANCELLED → LATE_SUCCESS / DUPLICATE_SUCCESS / CANCELLED_ORDER_SUCCESS → AUTO_REFUNDING → REFUNDED
```

一个业务订单在 Payment 中只有一个 `payment_order`，可以有多个历史 `payment_attempt`，但数据库唯一活动槽位保证最多一个活动尝试。重复创建支付优先返回现有活动尝试；失败或过期后才允许创建下一次尝试。

### 5.3 下单流程

1. 学生选择课程并提交课程 ID，客户端金额仅用于显示。
2. Order 向 Course 获取已发布、可销售的课程快照。
3. Order 根据课程快照计算应付金额；首期不支持优惠券或客户端折扣。
4. 使用幂等键创建订单和明细；价格、标题和封面形成快照。
5. Order 只创建付费订单；价格为零的课程通过 Course 免费选课接口幂等处理，不伪造支付事件。
6. 付费订单进入待支付，购物车项在订单创建成功后移除或标记已购买。

### 5.4 支付回调

1. Payment 保存回调摘要并以渠道通知 ID 去重。
2. 验证签名、商户、渠道订单、金额、币种、渠道支付时间和支付状态。
3. 锁定唯一 `payment_order`。第一个在订单有效期内成功的尝试成为接受成功，在本地事务中写 `PaymentSucceeded` Outbox。
4. Payment 已消费 `OrderCancelled` 时，把活动尝试置为取消并尽力关闭渠道；取消后仍成功扣款记录为 `CANCELLED_ORDER_SUCCESS`，自动创建全额退款，不发布 `PaymentSucceeded`。
5. 支付聚合已成功后其他尝试再次成功，记录为 `DUPLICATE_SUCCESS`，自动创建全额退款并告警，不重复发布 `PaymentSucceeded`。
6. 渠道支付时间晚于订单 `expiresAt`，记录为 `LATE_SUCCESS`，自动退款并发布异常事件，Order 保持关闭且不履约。
7. 相同回调重放返回渠道要求的成功响应，但不重复发事件或退款。
8. Order 消费正常 `PaymentSucceeded`：待支付订单变为 `PAID`；如果关闭任务先执行但 `providerPaidAt <= expiresAt`，允许通过专用对账迁移 `CLOSED → PAID`。若用户取消与回调并发且 Order 已为 `CANCELLED`，Order 不发布 `OrderPaid`，而是幂等发布含订单项金额分摊的 `PaymentCompensationRequested`；Payment 关系化保存分摊并自动全额退款。Order 消费补偿 `RefundSucceeded` 后更新取消订单各项已退金额但不产生选课。
9. Course 只消费 `OrderPaid` 幂等创建各订单项选课关系；补偿中的取消订单不会选课。
10. Notification 和 Analytics 异步处理，失败不回滚选课。

如果 Course 选课创建暂时失败，订单仍保持已支付，事件进入重试/死信和人工告警，不能把真实支付回退为未支付。

### 5.5 超时关闭与支付竞态

- Order 关闭任务使用版本条件更新 `PENDING_PAYMENT → CLOSED`，并记录关闭时间。
- 用户取消使用版本条件更新 `PENDING_PAYMENT → CANCELLED` 并发布 `OrderCancelled`；Payment 消费后关闭活动尝试。渠道关闭是尽力而为，最终安全仍由回调状态和 `PaymentCompensationRequested` 自动退款保证。
- Payment 创建尝试前读取 Order 可支付快照，尝试过期时间不得晚于订单过期时间。
- 活动槽位唯一索引和支付聚合行锁防止两个并发活动尝试。
- “支付时间在有效期内、事件晚到”按真实支付时间履约；“渠道在过期后扣款”不履约并自动退款。
- 重复扣款或晚到支付自动退款失败时保持 `AUTO_REFUNDING/FAILED` 事实、持续对账和人工告警，不把资金异常伪装成已解决。
- 自动/用户退款使用数据库唯一 `dedupKey`：取消竞态按订单、晚到/重复扣款按渠道交易、用户退款按退款申请。重复 `OrderCancelled/PaymentSucceeded/PaymentCompensationRequested` 或并发回调不得产生第二次退款。

### 5.6 退款

1. 学生发起退款申请，Order 按稳定顺序锁定所选订单项，服务端计算可退额并原子增加 `refundReservedAmount`；并发申请不得使“预留 + 已退”超过成交额。
2. 是否需要人工审核由退款策略决定；未确认业务政策时默认人工审核。
3. 多课程订单按订单项申请退款，服务端计算每项可退金额；通过后发布 `RefundRequested`，Payment 发起渠道退款。
4. 渠道退款成功后 Payment 发布 `RefundSucceeded`，只表达渠道资金事实。
5. Order 消费该事件，把订单项预留额原子转为已退款金额并按结果更新为部分或全部退款，然后发布带订单项、课程 ID 和已退金额的权威 `OrderRefunded`；驳回/取消申请则释放对应预留额。
6. Course 只消费 `OrderRefunded` 撤销对应已退款课程访问，不直接用 Payment 事件猜测订单项履约范围。
7. 已产生学习、成绩或证书记录时保留历史，不物理删除。

退款失败保留可重试和人工处理状态，不把订单错误标记为已退款。

## 6. 选课与学习进度

### 6.1 选课来源

- 免费课程：学生直接请求，Course 校验课程已发布并幂等创建。
- 付费课程：只接受可信 `OrderPaid` 事件，不接受浏览器直接传订单成功状态。
- 管理补录：需要单独权限、原因和审计。

### 6.2 进度上报

- 学生必须具有有效选课关系。
- 请求上报课件位置、观看增量和完成事件，不直接提交总百分比。
- 服务端限制异常大的观看增量和超出课件时长的位置。
- 同一课件进度使用乐观锁合并，不能因旧请求倒退。
- 课程完成度由可计入进度的课件及权重计算。
- 退款后进度历史保留，但访问按选课状态控制。

## 7. 作业

### 7.1 作业状态

```text
DRAFT → PUBLISHED → CLOSED
```

学生列表状态是投影：

- `PENDING`：已发布、未到期、无提交。
- `OVERDUE`：已到期且无提交，或提交被规则拒绝。
- `SUBMITTED`：存在待批改提交。
- `GRADED`：最新有效提交已评分。

### 7.2 发布

- 教师具有课程归属。
- 总分大于 0，截止时间晚于发布时间。
- `maxAttempts` 至少为 1。
- 发布后修改总分、截止时间等关键规则需要显式版本策略和审计。

### 7.3 提交

1. 学生具有有效选课关系。
2. 作业为已发布，未超过提交次数。
3. 超过截止时间时依据 `allowLateSubmission` 拒绝或标记迟交。
4. 保存新尝试版本和附件 ID，写 `AssignmentSubmitted`。
5. 相同幂等键不产生第二次尝试。

### 7.4 批改

- 只有课程教师可以批改。
- 分数必须在 `0..totalScore`。
- 使用提交版本防止两个教师覆盖彼此评分。
- 批改成功发布通知和分析事件。
- 需要学生重交时进入 `RETURNED`，并明确是否消耗尝试次数。

## 8. 考试

### 8.1 考试与答卷状态

```text
考试：DRAFT → PUBLISHED → ONGOING → ENDED
答卷：IN_PROGRESS → SUBMITTED → GRADED
```

### 8.2 发布

- 开始时间早于结束时间，考试时长为正。
- 题目分值合计必须等于总分。
- 客观题具有可判定答案；主观题允许无标准答案。
- 发布后题目形成版本，不能静默改变已开始答卷。

### 8.3 开始考试

1. 校验选课、考试时间窗口和尝试次数。
2. 幂等创建个人答卷和完整试卷快照。
3. `deadlineAt` 取个人开始时间加时长与考试结束时间的较早者。
4. 返回不包含隐藏答案和解析的题目。

### 8.4 保存与交卷

- 单题保存按答卷和题目唯一更新，使用版本防止旧答案覆盖新答案。
- 服务端根据 `deadlineAt` 裁决是否可保存和提交。
- 交卷接口幂等，首次交卷后答卷只读。
- 到期未主动交卷由调度任务自动交卷，并记录来源。
- 客观题在服务端自动评分；主观题完成后才进入 `GRADED`。
- 成绩发布策略决定学生何时能看到分数、正确答案和解析。

## 9. 直播

### 9.1 状态

```text
CREATED → LIVING → ENDED
回放：PENDING → PROCESSING → AVAILABLE / FAILED
```

- 创建和开始直播需要课程教师权限。
- 同一直播间不能同时有两个直播中场次。
- `ENDED` 不允许回到 `LIVING`；再次直播创建新场次。
- 学生进入时验证选课关系，教师进入时验证课程归属。
- 浏览器先通过 HTTPS 获取绑定用户和直播间的一次性短期连接票据，再建立 WebSocket；票据验证成功后立即失效。
- 聊天消息由服务端绑定发送者；频率和长度超限拒绝。
- 未配置媒体服务时只展示控制面状态，不生成虚假推流地址或在线人数。

## 10. 通知

1. Notification 消费来源领域事件。
2. 按事件 ID、接收人和模板幂等创建通知。
3. 站内收件箱先落库，外部渠道形成独立投递任务。
4. 外部投递失败按策略重试；最终失败告警但不修改来源业务。
5. 标记已读是当前用户范围内的幂等操作。

通知中的 `actionUrl` 必须来自受控路由模板，不能直接信任事件内任意 URL。

## 11. 学习社区

- 已登录用户发布内容，服务端写入真实作者。
- 帖子和评论长度、频率、课程可见性由服务端校验。
- 点赞、收藏使用唯一约束，重复添加返回现有状态。
- 作者可以编辑自己的内容；审核员可以隐藏，不能冒充作者修改正文。
- 删除使用可审计状态变更，保留审核和争议处理所需历史。
- 被下架课程的社区内容默认不可新增，历史展示策略由课程可见性决定。

## 12. 管理审核与配置

### 12.1 审核

- 课程审核由 Course 执行并引用不可变 `course_version`；课程目录审核由 Content 执行并引用不可变 `content_revision`。
- 拒绝原因必填并持久化；批准原因可选。
- 审核使用快照版本，目标内容已变化时返回版本冲突。
- 提交人可在审批前撤回；撤回后原版本不可重新审批，只能复制为新草稿版本再次提交。
- 审核者不能审核自己的提交。
- 所有审核结果发送通知并写审计事件。

### 12.2 系统配置

- 站点名称、Logo、备案号等非敏感配置可由 User 服务维护。
- SMTP、MinIO、JWT 和支付密钥不经普通读取接口返回。
- “测试连接”由对应服务执行并只返回成功、失败、时间和安全错误码。
- 产品 API 不提供密钥更新；生产通过 Kubernetes Secret/CI 受控发布，本地通过未提交 `.env`，管理页面只显示脱敏状态与测试结果。

## 13. 搜索、分析和推荐

### 13.1 搜索

- `CoursePublished/Changed/Offline` 驱动课程索引增删改。
- 只索引已发布、可见字段。
- 索引失败进入任务重试；全量重建通过新索引和别名切换完成。

### 13.2 分析

- Analytics 按事件构建日聚合和审计读模型。
- 事件迟到时可以重算受影响日期。
- 响应标注统计截止时间，避免把延迟视为实时事实。

### 13.3 推荐

- 首期规则输入为可用课程、热度、分类偏好和学习历史。
- 输出包含课程 ID、排名、分数、理由和规则版本。
- 推荐服务不可用时降级为热门课程或空结果。
- 推荐不会自动选课、购买或绕过可见性。

## 14. AI 助手边界

当前默认行为仍为 `【前端 Mock】`。真实 AI 助手必须在模型供应商、数据范围、权限、留存、内容安全和成本上限完成专项设计后，才允许通过 Gateway 暴露接口。

AI 输出只能作为辅助信息，不能自动评分、审核、退款、封禁账号或执行不可逆业务动作。

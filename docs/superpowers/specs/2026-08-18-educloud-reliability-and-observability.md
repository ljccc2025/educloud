# EduCloud 异常、可靠性与可观测性设计

> 状态：`【目标设计】`
>
> 目标：故障可隔离、可追踪、可补偿、可告警，不用虚假成功掩盖失败。

## 1. 异常分层

| 异常类别 | 产生位置 | HTTP | 是否记录 ERROR |
|---|---|---:|---|
| 参数校验 | Controller/DTO | 400 | 否，按 INFO/WARN 采样 |
| 未认证 | Security | 401 | 否，异常频率告警 |
| 无权限 | Security/Service | 403/404 | WARN 并记录安全审计 |
| 资源不存在 | Service | 404 | 否 |
| 状态/版本冲突 | Service | 409 | WARN |
| 业务规则失败 | Service | 422 | 否或 WARN |
| 依赖不可用 | Infrastructure | 503 | ERROR |
| 未预期系统错误 | 任意层 | 500 | ERROR，包含堆栈但不返回客户端 |

统一使用全局异常处理器。领域异常包含稳定错误码、可安全展示的消息和可选结构化上下文，不包含 SQL 或内部异常文本。

## 2. 错误码命名

格式为 `<DOMAIN>_<REASON>`，例如：

- 通用：`VALIDATION_FAILED`、`UNAUTHENTICATED`、`ACCESS_DENIED`、`VERSION_CONFLICT`。
- 用户：`USER_DISABLED`、`LOGIN_LOCKED`、`REFRESH_TOKEN_REUSED`。
- 课程：`COURSE_NOT_FOUND`、`COURSE_NOT_FOR_SALE`、`COURSE_AUDIT_CONFLICT`。
- 内容：`ASSIGNMENT_CLOSED`、`SUBMISSION_LIMIT_REACHED`、`EXAM_NOT_OPEN`、`EXAM_ALREADY_SUBMITTED`。
- 交易：`ORDER_STATUS_CONFLICT`、`PAYMENT_AMOUNT_MISMATCH`、`REFUND_NOT_ALLOWED`。
- 文件：`FILE_TYPE_NOT_ALLOWED`、`FILE_NOT_BOUND`、`FILE_ACCESS_DENIED`。
- 基础设施：`DEPENDENCY_UNAVAILABLE`、`MESSAGE_PUBLISH_FAILED`。

错误码一旦被前端或外部系统使用，不随意改名；废弃时保留兼容期。

## 3. 同步调用策略

### 3.1 超时

- 所有 Feign/HTTP 调用显式设置连接和读取超时。
- 普通查询、文件签名、支付渠道等使用不同超时配置，不采用一个全局大超时。
- Gateway 超时应大于服务内部预算但小于浏览器不可接受等待时间。
- 超时值在压测和运行数据后校准，未验证前不宣称容量目标。

### 3.2 重试

| 操作 | 自动重试 |
|---|---|
| 幂等 GET | 可有限重试并加抖动 |
| 带幂等键且服务端已保证去重的命令 | 可在明确网络失败时有限重试 |
| 创建支付、发起退款、发送外部邮件 | 不盲目重试；先查询或按业务唯一号恢复 |
| 数据库事务死锁 | 可在确认幂等和短事务后有限重试 |
| 参数、权限、业务冲突 | 不重试 |

重试次数必须有限，且总时间不能超过调用预算。每次重试记录计数指标，不为每次失败打印重复完整堆栈。

## 4. Outbox 与 Inbox

### 4.1 发布

1. 业务更新和 `outbox_event` 在同一数据库事务提交。
2. 发布器按状态和下次执行时间锁定小批事件。
3. 发布到 RabbitMQ 后更新为已发布。
4. 发布确认不明确时允许重新发送，依赖消费者幂等。
5. 达到重试阈值后标记失败并告警，不能静默丢弃。

### 4.2 消费

1. 读取事件并检查版本与必填字段。
2. 通过唯一 `event_id` 判断是否处理。
3. 投影队列按 `aggregateType` 绑定完整聚合事件流，不只绑定产生业务副作用的事件子集。比较 `aggregateVersion`：小于等于最后版本则忽略，等于最后版本加一时相关事件应用业务变更、无关事件记 `NO_OP` 并只推进版本，大于预期表示缺口并暂停该聚合。
4. 业务变更或 no-op 水位推进、投影最后版本和 Inbox 成功状态在同一本地事务提交。
5. 提交后确认消息。
6. 可重试失败进入延迟重试；不可重试格式错误进入死信。

生产者使用 `aggregateType + aggregateId` 形成稳定路由键，使同一聚合进入同一有序消费分区。即使 RabbitMQ 重投、多个消费者或死信重放打乱到达顺序，消费者仍以 `aggregateVersion` 防止旧事件复活状态。新投影第一次看见版本大于 1 时先以来源快照引导到明确版本；运行中版本缺口通过来源快照或 Outbox 归档校准后再继续。

RabbitMQ 不是永久重放源。发布成功的 Outbox 按数据库提交顺序 `sourceSequence` 归档保留；派生服务重建在 W1 前预绑定“来源全事件” durable 队列，不相关聚合 no-op 推进来源水位，再使用“已提交水位 W1 + 当前快照 + 结束水位 W2 + 有界 `(W1,W2]` 归档 + durable 实时队列”协议。目标追到新的已提交水位、无更早未确认消息并核对行数、金额汇总、最大版本、水位连续性和失败记录后才原子切换。任务持久化每来源水位、游标、队列名和暂存目标，崩溃后恢复而非重新猜测边界。普通事务投影只保证所依赖聚合类型的连续 `aggregateVersion`，不使用全来源水位。

### 4.3 死信处理

- 死信保留原事件 ID、来源、失败错误码、次数和最后时间。
- 运维人员先修复根因，再通过受审计的工具重放。
- 重放不修改原事件 ID，消费者仍保持幂等。
- 禁止直接删除死信来消除告警。

## 5. 业务补偿与对账

| 场景 | 补偿方式 |
|---|---|
| 支付成功但订单未更新 | Payment/Order 对账任务重发或重放事件 |
| 订单关闭与成功回调并发 | 根据渠道 `providerPaidAt` 和订单 `expiresAt` 裁决；有效期内履约，过期后自动退款 |
| 同一订单重复扣款 | 只接受首个成功，其他尝试自动退款并立即告警 |
| 订单已支付但未选课 | Course 消费重试、死信告警和按订单补录命令 |
| 渠道退款成功但订单项/访问未更新 | 向 Order 重放 `RefundSucceeded`，确认其发布 `OrderRefunded`；再向 Course 重放 `OrderRefunded` 并告警 |
| 通知投递失败 | Delivery Task 延迟重试；不回滚业务 |
| 搜索索引失败 | Index Task 重试或全量重建 |
| Analytics 漏事件 | 按水位回放或按日期重算 |
| Analytics/Recommendation 全量重建 | 记录来源水位，导出当前带版本快照，再重放水位后的 Outbox 归档并校验后切换 |
| 文件上传完成但未绑定 | 保留期后再次检查并清理 |

所有人工补偿需要权限、原因、前后状态和追踪 ID 审计。

## 6. 并发控制

- 聚合更新使用 `version` 乐观锁，冲突返回 409。
- 唯一索引保护重复选课、购物车项、点赞、收藏、回调和幂等键。
- Redis 锁只用于确有必要的短临界区，并设置持有者标识、TTL 和安全释放。
- 不使用长事务包裹网络调用。
- 支付回调先去重并锁定唯一支付聚合；活动槽位唯一。已终态后的额外成功进入重复扣款退款流程，不反向覆盖首个成功事实。
- 考试答题按答卷版本和题目唯一键防止旧请求覆盖新答案。

## 7. 降级

| 依赖 | 降级行为 |
|---|---|
| Search | 课程详情和已知 ID 查询仍由 Course 提供；搜索页显示服务暂不可用 |
| Recommendation | 返回缓存热门课程或空结果，并标记降级 |
| Analytics | 管理/教师统计显示截止时间或暂不可用，不阻止写业务 |
| Notification | 保留待投递任务，不回滚来源业务 |
| Payment | 订单保持待支付，不返回虚假成功 |
| MinIO | 上传失败明确返回，业务对象不绑定不可用文件 |
| Redis | 权威数据仍在数据库；会话和限流按安全优先策略处理 |

认证、授权和支付回调验证不能“失败开放”。

## 8. 应用日志

### 8.1 必备字段

```text
timestamp, level, service, environment, instance,
requestId, traceId, spanId, userId, operation,
httpMethod, path, httpStatus, durationMs,
errorCode, exceptionClass, message
```

- 生产使用结构化日志；本地可使用可读格式。
- `requestId` 和 `traceId` 从 Gateway 贯穿同步调用和事件信封；非 HTTP 调度任务生成自己的请求标识。
- 日志消息描述发生了什么、影响什么、是否会重试，不打印完整请求对象。
- 禁止使用 `System.out.println`、空 catch 或只打印 `e.getMessage()`。

### 8.2 脱敏

绝不记录密码、Access/Refresh Token、Cookie、JWT 私钥、SMTP/MinIO/支付/AI 密钥、完整银行卡信息。邮箱、手机号、IP、支付载荷按用途最小化和脱敏。

## 9. 审计日志

以下操作必须产生审计事实：

- 登录失败、会话重用、账号锁定和禁用。
- 角色、权限和用户状态变更。
- 课程、内容和社区审核。
- 订单、支付、退款和对账补偿。
- 作业、考试成绩变更与人工修正。
- 系统业务配置、文件删除、敏感数据导出。

审计字段：来源服务、操作者、角色、动作、资源类型和 ID、结果、原因、变更摘要、IP、User-Agent、`requestId/traceId`、发生时间。

来源服务保留权威审计，Analytics 只构建统一查询视图。普通管理员不能修改或清空审计事实。

每个产生上述动作的服务在自己的数据库本地事务中追加 `audit_event`，并通过 Outbox 发布 `AuditEventPublished`。应用数据库账号对该表只有 INSERT/SELECT，运维清理使用独立受审计账号和已批准保留策略。Analytics 丢失或重建不会影响来源审计证据。

## 10. 指标

### 10.1 通用技术指标

- HTTP 请求量、2xx/4xx/5xx、P50/P95/P99 延迟。
- JVM 堆、GC、线程、进程 CPU。
- 数据库连接池、获取等待、慢查询和事务回滚。
- Redis 请求失败、命中率、内存和连接。
- RabbitMQ 发布确认、积压、重试、消费失败和死信。
- Outbox 提交顺序行锁等待、分配吞吐和重建水位滞后；容量验收若证明单行序列成为瓶颈，先评估事件降采样/批量化，再通过专项架构决策调整，不静默放弃提交顺序保证。
- Elasticsearch 集群健康、查询延迟、索引失败。
- MinIO 上传/下载失败、耗时和容量。

### 10.2 业务指标

| 服务 | 指标 |
|---|---|
| User | 注册、登录成功/失败、锁定、活跃会话 |
| Course | 发布、审核时长、选课成功/失败、评价 |
| Content | 学习完成、提交、批改积压、交卷和评分 |
| Order | 创建、取消、超时、支付转化、退款申请 |
| Payment | 成功率、回调重复、金额不匹配、退款和对账差异 |
| Live | 直播中场次、进入失败、连接数、消息拒绝 |
| Notification | 待投递、成功、失败和重试 |
| Search | 查询延迟、零结果、索引延迟和失败任务 |
| Analytics | 事件延迟、水位和重算状态 |

业务指标不得把模拟数据与生产真实数据混合展示。

## 11. 链路追踪

- Gateway 为请求创建或传递 Trace，并把上下文传给所有同步调用。
- Outbox 事件保存来源 `traceId`，消费者创建新 Span 并关联事件。
- 支付回调、调度任务和人工补偿创建新的根 Trace，并关联业务号。
- 高流量场景的采样率可配置，但错误、慢请求和关键交易优先保留。
- Trace 标签不保存密码、Token、课件正文或完整答卷。

## 12. 健康检查

### 存活

只判断进程是否仍能运行。不因数据库短暂不可用立即判定进程死亡，避免无限重启。

### 就绪

判断实例是否可以接收新流量。数据库、关键配置或消息发布能力不可用时按服务职责影响就绪状态。

### 优雅停机

- Nacos/Kubernetes 先停止分配新流量。
- 等待进行中 HTTP 请求在预算内结束。
- 停止领取新消息，完成或安全退回已领取消息。
- 超时后终止并由幂等机制恢复。

## 13. 初始告警基线

下列阈值是上线前的初始值，不代表已经通过容量验证：

- 5 分钟内 5xx 比率持续超过 2%。
- 普通 API P95 持续超过 1 秒，或关键交易延迟显著偏离基线。
- RabbitMQ 队列持续增长、出现死信或 Outbox 失败事件。
- 支付金额不一致、签名失败或对账差异出现。
- 数据库连接池长期接近耗尽或持续慢查询。
- Elasticsearch 非绿色健康或索引任务持续失败。
- 磁盘、MinIO 容量达到预警水位。
- 认证失败、权限拒绝或 Token 重用出现异常突增。

最终阈值必须通过压测和真实流量校准，并注明统计窗口、严重级别、接收人和处理手册。

## 14. 事件响应

1. 告警关联服务、环境、仪表盘、最近发布和 Runbook。
2. 先控制影响：停止错误发布、隔离异常实例或关闭非核心入口。
3. 使用 `requestId/traceId`、业务号和事件 ID定位。
4. 执行已验证补偿，禁止直接改库作为默认处理方式。
5. 恢复后核对数据一致性和积压。
6. 记录根因、影响、修复、验证和预防措施。

没有实际恢复证据时，不能只因为告警消失就宣称问题已解决。

# 学生端课程购买闭环与真实支付预留设计

## 1. 目标

修复学生端“课程中心 → 课程详情 → 立即购买”错误返回课程列表的问题，并建立可直接运行的 MOCK 购买闭环。购买成功后必须形成订单、更新课程访问状态、进入明确的支付结果页，并在课程详情、“我的课程”和“我的订单”中保持一致。

本次采用用户确认的 A 方案“独立结算页”。当前阶段只实现 MOCK 支付，但前端页面、订单状态、支付适配器和结果确认流程必须按照真实支付边界设计，后续接入支付宝或微信时不得重写购买主流程，也不得把浏览器返回结果当作可信支付事实。

## 2. 现状与问题根因

### 2.1 当前错误行为

`CourseDetail.tsx` 的“立即购买”按钮当前依次执行：

```text
handleAddToCart()
  → navigate('/courses')
```

因此按钮只把课程加入内存购物车，随后硬编码跳回全部课程页。它没有创建订单、发起支付、更新课程权限或展示支付结果，这正是用户看到“点击购买后返回上一个界面”的直接原因。

### 2.2 可复用的现有能力

学生端已具备以下基础：

- `orderApi.create(courseId)` 能创建 MOCK 订单并更新课程 `enrolled` 状态，但当前直接生成 `PAID`，未表达待支付和确认过程；
- `courseApi.enroll(id)` 可支持免费课程幂等选课；
- `Order` 已包含订单号、课程快照、金额、支付方式和订单状态；
- `/orders`、`/my-courses`、`/learn/:courseId` 已存在受保护路由；
- `useCartStore` 已提供按课程移除购物车项的能力。

这些能力应被纳入统一购买流程，不另建平行的订单或选课数据源。

### 2.3 与后端总体规范的关系

本设计遵循项目既有后端规范：

- 业务订单状态使用 `PENDING_PAYMENT → PAID`，并允许进入 `CANCELLED/CLOSED`；
- Payment 聚合和支付尝试分别维护处理状态，不能把“支付处理中”伪装成订单已支付；
- 付费课程只因可信 `OrderPaid` 结果产生选课，浏览器不能直接声明支付成功；
- 免费课程由 Course 幂等选课，不创建虚假支付订单；
- 创建订单、创建支付和处理回调均要求幂等。

前端 MOCK 层可继续映射现有简化类型，但页面语义和 API 边界必须与上述正式模型一致。

## 3. 用户可见流程

### 3.1 入口判定

课程详情购买卡片根据课程与登录状态展示唯一主操作：

| 条件 | 主操作 | 结果 |
|---|---|---|
| 已选课且有访问权 | “继续学习” | 进入 `/learn/:courseId` |
| 免费课程且未选课 | “免费加入学习” | 幂等选课后进入学习页 |
| 付费课程、未登录 | “立即购买” | 登录后回到该课程结算页 |
| 付费课程、已登录且未购买 | “立即购买” | 进入 `/checkout/:courseId` |
| 已有待支付订单 | “继续支付” | 恢复同一订单的结算/支付状态 |

未登录跳转必须携带受控站内返回地址，例如 `/login?redirect=/checkout/6`。登录页只接受白名单站内路径，禁止开放重定向。

### 3.2 独立结算页

新增受保护路由 `/checkout/:courseId`。页面展示：

- 课程封面、名称、讲师和课程级别；
- 原价、优惠金额和服务端权威实付金额；
- 支付方式选择：支付宝、微信支付；
- 购买协议、永久访问说明和退款规则；
- 主按钮“确认支付 ¥金额”；
- 次入口“返回课程详情”。

首期尚未实现优惠券，结算页不得出现可输入但不会生效的优惠券控件。客户端展示金额仅用于确认，创建订单和支付时不把客户端金额作为可信参数。

### 3.3 确认支付

用户点击确认后按以下顺序执行：

```text
检查课程与现有订单
  → 幂等创建或恢复 PENDING_PAYMENT 订单
  → 为订单创建或恢复活动支付尝试
  → 支付界面进入“支付结果确认中”
  → 查询权威订单/支付状态
  → PAID 后进入支付成功页
```

支付按钮在请求期间禁用并显示加载状态。重复点击、刷新页面或网络重试必须复用同一幂等订单和活动支付尝试，不能重复扣款或生成多笔活动订单。

### 3.4 支付成功页

新增受保护路由 `/checkout/success/:orderId`。成功页展示：

- 明确的“购买成功，课程已加入我的课程”；
- 课程名称、订单号、实付金额和支付方式；
- 主按钮“开始学习”；
- 次按钮“查看订单”；
- 辅助入口“返回课程详情”。

成功页只在重新查询权威订单状态为 `PAID` 后展示成功语义。通过地址栏直接访问、浏览器返回或伪造路由参数均不能制造购买成功状态。

### 3.5 成功后的状态同步

订单确认 `PAID` 后：

- 重新读取课程/选课状态，等待或确认课程访问权已开通；
- 课程详情按钮变为“开始学习”或“继续学习”；
- 课程从购物车移除；
- “我的课程”出现该课程；
- “我的订单”显示同一订单为已支付；
- 再次进入结算页时直接引导学习，不允许重复购买。

购物车移除时点以项目总体规范为准：正式后端可在订单创建成功后移除；当前前端 MOCK 为避免失败后丢失入口，在确认 `PAID` 后移除。两者都不得在仅点击“立即购买”时移除。

## 4. 页面和组件边界

### 4.1 页面

- `Checkout`：负责课程快照、订单恢复、支付方式选择和发起支付；
- `CheckoutSuccess`：只负责查询并展示已支付订单结果；
- `CourseDetail`：负责入口判定和跳转，不直接编排支付状态；
- `Orders`：继续作为订单查询和待支付订单恢复入口；
- `Login`：成功后消费并清除受控返回地址。

### 4.2 展示组件

组件拆分为以下无业务状态组件：

- `CheckoutCourseSummary`：课程与金额摘要；
- `PaymentMethodSelector`：支付宝/微信选择；
- `PaymentStatusPanel`：处理中、失败、取消和确认中反馈；
- `PurchaseSuccessCard`：成功结果与后续动作。

页面持有流程状态，展示组件不直接修改订单、课程或购物车 Store。

### 4.3 路由保护

`/checkout/:courseId` 与 `/checkout/success/:orderId` 必须使用现有 `ProtectedRoute`。访问成功页时还要校验订单归属当前用户，不能仅依赖已登录状态。

## 5. 前端支付抽象

### 5.1 统一契约

业务页面只依赖支付网关接口：

```ts
interface PaymentGateway {
  initiate(request: PaymentRequest): Promise<PaymentInitiation>;
  query(orderId: string): Promise<PaymentStatusSnapshot>;
}
```

采用以下适配器边界：

- `MockPaymentGateway`：当前阶段使用，模拟渠道创建、确认延迟、成功、失败和取消；
- `AlipayPaymentGateway`：后续接入，只负责处理支付宝跳转/二维码所需的前端参数；
- `WechatPaymentGateway`：后续接入，只负责处理微信支付跳转/二维码所需的前端参数。

页面不使用渠道分支直接修改订单。所有适配器返回统一的 `paymentId`、`attemptId`、展示状态和渠道动作信息。

### 5.2 MOCK 与真实支付共用的语义

MOCK 不能直接把“确认支付”解释为同步成功。它应模拟正式流程：

```text
订单 PENDING_PAYMENT
  → 支付尝试 ACTIVE / 支付聚合 PROCESSING
  → MOCK 渠道确认
  → 支付 SUCCESS
  → 订单 PAID
  → 课程访问开通
```

页面级状态统一使用 `IDLE/CREATING_ORDER/AWAITING_PAYMENT/CONFIRMING/SUCCEEDED/FAILED/CANCELLED`，但这些仅用于 UI 展示，不能替代订单和支付领域状态。

### 5.3 真实支付可信边界

真实支付接入必须满足：

1. 后端创建待支付订单并计算权威金额；
2. `POST /payments` 只提交 `orderId` 和支付渠道；
3. 支付渠道异步回调由后端验签；
4. 后端验证商户、渠道订单号、金额、币种、支付状态和渠道支付时间；
5. 回调按渠道通知 ID 幂等处理；
6. 第一个合法成功结果才能发布支付成功事实；
7. Order 消费可信支付结果后进入 `PAID`，Course 再据此开通访问；
8. 浏览器返回页只查询状态，不能自行把订单更新为 `PAID`。

因此当前交付只能描述为“MOCK 支付闭环，已预留真实支付适配器”，不得宣称支付宝或微信真实支付已经接通。

## 6. 数据与 API 契约

### 6.1 前端类型演进

前端 `OrderStatus` 统一采用后端命名并同步调整现有订单页：`PENDING_PAYMENT/PAID/CANCELLED/CLOSED/REFUNDING/PARTIALLY_REFUNDED/REFUNDED`。删除原有简写 `PENDING`，不得在页面内混用两套字符串。支付处理中和支付失败放在支付快照/页面状态中，不把 `PROCESSING/FAILED` 错加为业务订单状态。

订单至少需要：

- `id/orderNo/courseId/courseTitle/courseCover`；
- `originalAmount/payableAmount/currency`；
- `paymentMethod/status/createdAt/expiresAt/paidAt`；
- 支付结果页需要的订单归属和支付摘要。

### 6.2 MOCK API

将当前一次性 `orderApi.create()` 拆成与正式接口同构的职责：

- `getPayableOrderByCourse(courseId)`：查询可恢复的待支付订单或已购买结果；
- `create(courseId, idempotencyKey)`：创建 `PENDING_PAYMENT` 订单；
- `getById(orderId)`：读取权威订单状态；
- `cancel(orderId)`：取消仍可取消的订单；
- `paymentApi.create(orderId, channel)`：创建或恢复活动支付尝试；
- `paymentApi.getByOrderId(orderId)`：供结算页、结果页和刷新恢复查询支付状态；
- `courseApi.enroll(courseId)`：只处理免费课程。

MOCK 数据仍可驻留内存，但接口形态和状态流转要与后续后端一致。页面不得直接修改 `courses` 或 `orders` 数组。

### 6.3 幂等规则

- 创建订单：每次显式购买意图生成稳定幂等键；请求重试沿用同一键；
- 同一用户、同一课程已有 `PAID` 订单/有效选课时返回已购买结果；
- 同一用户、同一课程已有未过期 `PENDING_PAYMENT` 订单时恢复原订单；
- 创建支付：同一订单存在活动尝试时返回原尝试；失败、取消或过期后才允许重新创建；
- 前端按钮防抖只改善体验，最终去重必须由 API/数据库约束保证。

## 7. 异常与恢复设计

| 场景 | 页面行为 | 数据约束 |
|---|---|---|
| 创建订单失败 | 留在结算页，保留支付方式并允许重试 | 不产生课程权限 |
| 支付发起失败 | 展示原因和“重新支付” | 订单仍为待支付 |
| 用户取消支付 | 返回结算状态 | 不开通课程 |
| 回调延迟或事件延迟 | 显示“支付结果确认中”，限时轮询 | 不提前展示成功 |
| 页面刷新/浏览器返回 | 使用路由订单号重新查询 | 不依赖组件内存恢复 |
| 重复点击 | 禁用按钮并复用幂等键 | 只允许一个活动尝试 |
| 已购买后再次进入 | 直接引导学习 | 不创建新订单 |
| 订单超时 | 显示已关闭并允许重新下单 | 原订单进入 `CLOSED` |
| 金额或课程状态变化 | 重新拉取权威报价并要求用户确认 | 客户端金额不参与裁决 |
| 支付成功但访问权尚未投影 | 显示“购买成功，课程正在开通”并重试查询 | 订单不可回退为未支付 |
| 支付成功但前端断网 | 订单页/成功页重新查询后恢复 | 成功事实保存在服务端 |

真实支付还必须处理晚到成功、重复成功和取消竞态，按总体后端规范自动退款并告警；前端只展示权威订单/退款状态，不自行推断已经解决。

## 8. 视觉与交互规范

- 结算页延续学生端象牙白背景、靛蓝主色、琥珀优惠色和轻量玻璃卡片语言；
- 关键信息按“课程摘要 → 金额 → 支付方式 → 协议 → 确认支付”排列；
- 支付主按钮在桌面端位于金额卡片底部，移动端保持可见但不能遮挡协议；
- 支付方式必须同时使用图标、名称和选中标识，不能只靠颜色表达；
- 加载、失败、取消、确认中和成功均有文本反馈；
- 动效遵循 `prefers-reduced-motion`，支付状态不使用持续高成本模糊或大面积动画；
- 成功页主动作是“开始学习”，不自动跳回全部课程页。

## 9. 变更边界

实施预计涉及学生端以下范围：

- 课程详情购买入口；
- 结算页和支付成功页；
- 路由与登录返回地址；
- Order/Payment 类型和 MOCK API；
- 购物车移除与课程状态刷新；
- 订单页待支付恢复入口；
- 相应自动化测试或浏览器回归。

明确不在本阶段实现：

- 真实支付宝/微信商户签约、密钥、SDK、回调和对账；
- 优惠券、组合订单、发票或分期支付；
- 退款流程重构；
- 后端微服务实体落地或生产部署。

工作区存在大量用户未提交改动。实现必须使用精确补丁，禁止覆盖、格式化、删除或提交无关文件。

## 10. 验证策略

### 10.1 修复前红灯

- 在课程详情点击“立即购买”；
- 断言当前错误进入 `/courses`；
- 断言未出现结算页和成功页；
- 断言没有待支付订单或可信购买结果。

该回归必须在实现前失败，证明测试能够捕获当前缺陷。

### 10.2 核心绿灯

- 付费课程点击“立即购买”进入正确课程的结算页；
- 未登录用户登录后返回原结算页；
- MOCK 支付成功后进入正确订单的成功页；
- 成功页、课程详情、“我的课程”和“我的订单”状态一致；
- 成功后按钮变为“开始学习”，购物车不再包含该课程；
- 免费课程直接选课，不创建支付订单；
- 已购买课程不会产生重复订单；
- 待支付订单可从课程详情和订单页恢复；
- 刷新确认中/成功页面可恢复状态；
- 直接伪造成功页 URL 不能获得成功状态或课程权限。

### 10.3 异常与幂等

- MOCK 支付失败后可以重试；
- 用户取消支付后不产生课程权限；
- 连续点击和网络重放只创建一笔订单、一个活动支付尝试；
- 回调延迟期间只显示确认中；
- 订单超时后不能继续支付，可重新创建新订单；
- 金额变化时阻止使用旧金额支付；
- 支付成功、访问投影延迟时保留成功事实并最终进入学习。

### 10.4 工程检查

- 学生端 TypeScript 类型检查通过；
- 学生端生产构建通过；
- 购买路径浏览器回归通过；
- 浏览器控制台没有新增错误；
- 目标文件差异空白检查通过；
- 原有用户改动保持不变。

## 11. 成功标准

学生从课程详情点击“立即购买”后进入独立结算页，完成可观察、可恢复、不可重复的 MOCK 支付闭环；支付成功后明确进入结果页并获得课程访问入口，不再返回全部课程页。MOCK 与未来真实支付使用相同的订单、支付和结果确认语义，且文档明确区分“已完成 MOCK 支付”和“尚未接通真实支付渠道”。
